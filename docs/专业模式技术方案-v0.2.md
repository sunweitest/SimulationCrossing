# 专业模式技术方案（修订稿 v0.2）

> 状态：讨论稿，建议先做限量灰度。  
> 目标：让一场剧情像一局多人博弈——NPC 有自己的目标、受限的信息和可见行动，战斗与谈判能产生持续后果。  
> 兼容原则：娱乐模式仍是默认；专业模式按存档启用，复用现有剧情、配额、存档和 SSE 主链路。

## 结论先行

建议做专业模式，但不要把卖点写成“开了 thinking”或“多调了几个 agent”。玩家应当能感受到三件事：

1. NPC 会为自己的目标主动行动，而不只是回应玩家。
2. NPC 只根据自己见过、听说或推断的内容行动，秘密能够被保留和揭穿。
3. 战斗、谈判等关键场面有明确目标、风险、进展和代价，结果会改变后续局势。

推荐的最小闭环是：**导演定局势 → 最多 3 名 NPC 各自决策 → 统一结算冲突 → 叙事呈现结果 → 更新世界状态与记忆**。NPC 不进行无限轮自由聊天；thinking 只用于少数需要全局判断的节点，原始思维链不展示给玩家。

## 现状核对（基于当前仓库）

- 主行动流是 `POST /api/game/action/stream`，SSE 事件为 `status`、`story_chunk`、`scene`、`done`、`error`。前端已有流式解析器。
- `GameSession` 有场景、使命、积分和 `characters_state`，但没有对局模式、结构化 NPC 目标或角色知识边界。
- DeepSeek provider 已有 `query_character` 工具调用；它能查人物资料，不等于每个 NPC 有独立目标、局部记忆和自主行动。
- 数据库使用 SQLAlchemy async + asyncpg。现有回溯接口是 `/session/{id}/rewind`，会删除目标回合之后的记录并重算部分存档状态。

因此不建议先新增平行的 `/action/pro/stream`、LangGraph Postgres saver 和第二套回溯接口。先在现有行动入口按 session mode 分流，并用现有数据库栈保存专业模式的执行状态。

## 产品范围与边界

### 玩家体验

开局选择“娱乐 / 专业”，存档记住该选择。专业模式每回合给出轻量阶段提示，例如“局势整理 → NPC 行动 → 结果结算 → 剧情展开”；可选展示简短的**公开行动卡**，不展示 NPC 私密想法或模型思维链。玩家仍用自然语言输入，仍收到可选行动。

专业模式不保证更长、更华丽的文本；重点是角色行为和局势状态能跨回合保持一致。建议先在 2 个 NPC 关系密集的世界灰度，按人物数据质量筛选，不把首版绑定成“只能玩固定三世界”。

### 首版明确不做

- 多人实时联机、语音或 NPC 间无限自由对话。
- 向量数据库、跨存档共享记忆或完整战棋系统。
- 公开模型推理过程；给玩家展示的是意图、证据和结果摘要。
- 以未经验证的成本倍数、固定延迟承诺或付费墙作为上线前提。

## 一回合的执行流程

```text
读取 session 与当前状态
  → 选择在场角色（规则、地点、最近互动）
  → 按每个角色的知识范围准备独立上下文
  → Director 产出本幕目标、压力与公开约束
  → NPC agents 并行提交各自的意图/行动（上限 3 人）
  → Resolver 结算玩家行动与 NPC 行动的冲突
  → Narrator 流式写出可见结果
  → 生成选项、使命判定、事实与关系变化
  → 一次性提交本回合状态
```

Director 可以看全局状态，但必须输出分开的 `public_brief` 与 `private_constraints`。每个 NPC prompt 由服务端单独组装，只含该 NPC 的身份、目标、关系、已知事实和它能感知的本幕信息；不能把完整 state 或其他 NPC 私密计划透传给它。NPC 输出是结构化行动数据，不让 NPC agent 直接修改数据库。

### 战斗与谈判：共用一个“冲突框架”

专业模式的特色不应止于人物多。对抗场面统一形成一个简洁的冲突框架：`goal`（本幕想达成什么）、`opponents`、`stakes`（失败代价）、`progress`（进展）、`pressure`（剩余时间或恶化因素）。谈判、追查、逃脱与战斗都走相同回合流程，Resolver 返回 `success / partial / fail`、依据摘要、代价和状态变更；Narrator 再把结算写成剧情。

首版使用可校验的结构化裁决与显式证据，不声称是精确战棋或完全确定性模拟。不要让文笔模型在故事正文里悄悄决定胜负。后续若玩家反馈需要更强公平性，再增加少量可见属性与可复现随机种子，避免首版就引入大套 RPG 数值。

## 状态与记忆设计

### 会话和回合

- `game_sessions.mode`：`fun` / `pro`，默认 `fun`。
- 新增 `pro_turn_runs`（或等价表）：存档、回合号、客户端生成并在重试时复用的 `turn_request_id`、阶段、状态、玩家行动、阶段产物 JSON、开始/完成时间及成本统计。对 `(session_id, turn_request_id)` 加唯一约束；另用活动运行的部分唯一索引或等价的会话级锁，防止同一存档并发推进两个回合。同一个请求重试时续用已完成阶段，不能重复结算或扣配额。
- 每个阶段完成后先持久化阶段产物，再继续执行。最终场景、状态和回合结果在同一数据库事务内提交；只有提交成功后才发 `scene` / `done`。
- 保存的阶段产物是专业模式的恢复点。首版不引入 LangGraph saver：它不能自动保证模型调用、业务数据库提交和配额扣减的原子性，还会引入 psycopg3 与 asyncpg 双连接池。若之后需要图分支、人工中断再评估 LangGraph。

### 事实与知识可见性

为 NPC 使用稳定的 `character_key`，不要只靠显示姓名识别。每条事实至少包含：`text`、`turn`、`source_event`、`known_by`、`visibility`、`kind`。事实召回由服务端过滤，prompt 里只放当前 NPC 可访问的记录。

- `known_by` 表示明确知道它的角色；公开场景由在场记录或明确公开规则派生。
- 私下对话只授予参与者；目击、转告、传闻和推断要区分来源，传闻不能变成确定事实。
- 不明来源或不明受众的事实按私有处理，不默认公开；导演的全局视角不能自动授予 NPC。
- LLM 可以建议事实与受众，服务端根据场景参与者、事件类型和明确收件人校验后才写入。不要单靠模型自律保证保密。
- NPC 行动卡只显示公开行动；秘密行动进入私有状态，等玩家发现后再揭示。

## 模型与 thinking 策略

按任务定义 provider 能力，而不是假设所有 provider 共用一个参数：

| 节点 | 建议配置 | 原因 |
|---|---|---|
| Director | 主模型；允许 thinking（若 provider 支持）；短结构输出 | 需要协调目标、节拍和约束 |
| NPC agents | 便宜快速模型；默认不启 thinking；每人短输出并行 | 角色局部决策，控制成本 |
| Resolver | 主模型或规则；结构化结算；必要时启 thinking | 关键后果需自洽且可解释 |
| Narrator | 当前主叙事模型，流式 | 文字体验；沿用现有首字超时与故障转移 |
| options / metadata | 复用当前实现 | 避免重复建设 |

为专业节点增加按 provider 能力校验的 thinking 开关和独立 token 上限。先用当前配置的实际模型做兼容性验证；不支持 thinking 的 provider 走相同结构化流程但关闭该能力。思维链不记录、不返回客户端，持久化的是可审计的结论字段，如 `intent`、`evidence`、`outcome`。

## API、SSE 与前端接入

- `GameSessionCreate` 增加可选 `mode`（默认 `fun`），模式与角色创建请求一同提交。
- 行动继续使用 `/api/game/action/stream`；后端根据存档 mode 分流。同步 `/action` 若保留，应走同一模式判定，避免非流式 API 绕过模式规则。
- 保持既有 `status`、`story_chunk`、`scene`、`done`、`error` 事件语义。专业模式只添加可选事件，例如 `agent_activity`（仅公开的角色与行动摘要）；旧客户端忽略未知事件仍能消费最终 `scene`。
- 在 `CharacterCreateView` 增加模式选择；`GameView` 展示阶段提示和可折叠的公开行动卡；存档列表显示模式徽标。沿用现有 `/rewind`：专业模式恢复所选回合的完整状态快照，娱乐模式保留原行为。
- 只增加实现需要的存档字段、事实表和回合运行表。迁移 revision 接在当前真实 head 后，禁止复用草案中的旧 revision 链。

## 失败、恢复和费用控制

| 情况 | 行为 |
|---|---|
| Director 失败 | 跳过专业编排，使用当前娱乐模式生成回合，并在结果标记 `fallback_used` |
| 单个 NPC 失败 | 该角色本回合不行动，其他角色继续 |
| Resolver 输出无效 | 最多一次受限重试；失败后采用保守的 `partial` 结果并记录原因 |
| Narrator 失败 | 使用现有主备 provider 和兜底文案；不要重跑已保存的 NPC 行动 |
| 进程中断 | 同一 `pro_turn_run` 续跑最近一个未完成阶段；阶段调用需幂等 |
| 最终提交失败 | 不发 `done`，保留可重试运行记录；重试不重复累计积分、使命或配额 |

专业模式默认关闭灰度开关，先给内部/小流量用户试用；每回合限制在场 NPC 数、各节点输入输出 token 和总调用时限。按真实账单与日志比较娱乐/专业模式成本和延迟，再决定免费体验次数、付费范围和目标。`agent_runs` 记录节点名、模型、token、耗时、成功状态；不记录 API 密钥、完整私密 prompt 或 reasoning 内容。

## 实施顺序与验收

### P0：能力验证与骨架

确认当前 DeepSeek / DashScope 配置对 thinking 参数、并行请求、结构化 JSON 和流式输出的支持；增加模式字段与服务端 feature flag；完成一条 Director → 1 名 NPC → Resolver → Narrator 链路。验收：娱乐模式请求与存档行为不变；专业存档可以完整走通并能降级。

### P1：多角色与局部知识

扩展至最多 3 名并行 NPC，建立稳定角色 key、事实写入/过滤、回合阶段持久化与幂等恢复；增加 UI 阶段提示和公开行动卡。验收：制作“只有 A 知道秘密”的场景集，逐项检查 B 不会直接复述秘密；断在各阶段重试不产生重复剧情提交或积分。

### P2：冲突框架与回溯

为谈判、战斗、追查和逃脱接入目标/筹码/进展/代价；将完整专业状态快照接入现有回溯接口；补充成本面板和灰度运营开关。验收：同一行动的结算状态与叙事一致；回溯后角色关系、使命、事实和积分与目标回合一致。

### 上线门槛

- 娱乐模式回归按项目现有 QA 套件验收，行为和接口保持兼容。
- 知识隔离用例通过率 ≥ 90%；至少 10 局人工试玩中，NPC 主动推动局势 ≥ 7 局。
- 采集至少 50 个专业模式回合的 P50/P95 延迟、失败率和 token/账单；先观测，不提前承诺固定倍数或秒数。
- 确认重复请求、中断恢复、回溯、降级和配额结算均可解释、可重复验证。

## 推荐默认决策

1. **可见范围**：先内部/小流量灰度，配额按实际成本数据再定。
2. **默认模式**：新局默认娱乐，用户主动选择专业。
3. **首版范围**：P0 + P1，先验证 NPC 主动性和知识隔离；P2 根据试玩反馈排期。
4. **世界范围**：选 2 个角色关系数据较完整的世界试点，按质量而非固定题材清单扩展。

此方案把 thinking 当作可选的推理能力，把 agent 当作有明确权限边界的行动者；真正的产品价值来自局势、角色知识和后果能够跨回合保存。
