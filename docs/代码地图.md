# 代码地图

> 目的：改一个功能时能**一次找对文件**。按「功能 → 前端 → 接口 → 后端 → 数据 → 配置」排列。
> 行号会漂移，所以定位一律用函数名/关键字，最后附了常用 grep。

## 1. 一图看整体

```
浏览器
  └─ nginx:8080        frontend/dist（Vue3 SPA） + /api 反代
       └─ uvicorn:8000  FastAPI
            ├─ middleware/rate_limit.py   次数限制（每次行动前检查、成功后计数）
            ├─ api/*.py                   路由层：鉴权、归属校验、组装响应
            ├─ services/game_service.py   业务编排：拼消息、调 LLM、存场景、算积分
            ├─ services/llm/*.py          LLM 适配（DeepSeek / DashScope）
            ├─ services/scene_image_matcher.py  场景图匹配（阿里云 embedding）
            └─ PostgreSQL（内容/存档） + Redis（次数计数）
```

## 8. 改动后的验收口径

1. 后端：`systemctl restart novel-backend` → `curl /health` → 打一次 `/api/game/action`（非流式）与 `/api/game/action/stream`（流式）都要 200 且有正文
2. 前端：`npm run build`（**必须用 `www-data` 用户跑**）→ 刷新页面看真实 DOM，不只看接口
3. 次数相关：Redis 里 `rate_limit:*` 有值、顶栏数字随行动变化、游客 429 出 toast、登录用户 429 出弹窗
4. 别在有人正在玩的时候 `redis-cli DEL rate_limit:*`，会把当日额度清空

## 12. 公共图库（场景配图怎么共享）

`frontend/public/images/scene/*.png` 是**一个所有世界共用的图库**：匹配器只按文件名做语义向量，
所以任何世界的剧情都可能命中任何一张图。为了让「共享」真的划得来，配了世界标签：

```json
// content/scene_images.json
{
  "深宅庭院廊下夜灯": ["通用"],
  "市井长街两侧店铺幌子": ["通用"],
  "辐射尘中的城市废墟": ["废土末世"],
  "云海之上破碎的山峰": ["仙侠修真", "封神演义", "武侠江湖"]
}
```

匹配规则（`scene_image_matcher.find_best_match(text, novel=...)`）：

1. 先在该世界可用的图里挑（`通用` + 本世界专属）
2. 本世界没有合适图（低于阈值 0.26）就退回全库
3. 都低于阈值 → 不返回图片，前端用世界封面兜底

所以新增世界不必为每个世界画 13 张：往公共图库补**跨世界通用**的场景（庭院、街市、客栈、
宫门、渡口、山道、雨夜、雪夜…）性价比最高；只有题材真的很特别的（废土）才做专属图。

```bash
# 生成一批通用场景图（提示词在 scripts/prompts/commons*.json）
/opt/venv/bin/python scripts/gen_images.py --prompts scripts/prompts/commons.json --install
# 加完图更新标签清单，然后重启后端重建向量缓存
sudo systemctl restart novel-backend    # 日志：TAGS: 56 张图，其中 17 张为世界专属
```

## 13. 使命系统（主线任务）

目的：阻止剧情无限滑向支线细节。每个「角色 × 时间节点」最多一个使命，三层结构：

```
content/worlds/*.json → characters[].timelines[<节点>].mission
{ "title": "让门重新认人",
  "goal": "三天内修好门禁，放人进来，别把掠夺者一起放进来",
  "stages": [{"name": "拿到旧工牌", "detail": "去行政楼翻抽屉"}, ...],
  "deadline_turns": 12,
  "stakes": "一百多人在门外，门开错一次就全完了" }
```

运行期状态在 `game_sessions.mission_state`：
`{mission, stage_index, deadline_turns, days_left, turns_used, penalty, status, last_label, last_note, log}`

流程：
1. 开局 `GameService.init_mission_state()` 把定义复制成进度（复制而非引用，改内容不影响已有存档）。
2. 每回合 `_build_mission_block()` 把使命/阶段/剩余回合/写作要求注入提示词——这是减少支线的关键。
3. 每回合 `judge_mission()` 独立判定（并行跑，不增加等待）：输出 `advance / stage_done / setback / note`。
   **不要**把判定塞进选项生成：一个模型同时干五件事时，`stage_done` 几乎永远判 false。
4. `GameService.apply_mission_update()` 结算：阶段达成 +10 分、全部完成 +20 分、每回合耗 1 回合、恶化再 +1（上限为期限的 1/3）。
5. 前端 `GameView` 顶部使命条：阶段 i/n + 剩余回合 + 本回合「推进/停滞/恶化」，点开看完整阶段列表。

坑：
- **JSON 列必须整体赋值**。`ms = session.mission_state; ms["x"]=1; session.mission_state=dict(ms)` 也会丢更新——属性事件记录的旧值与新值是同一个对象，flush 判定“无变化”。正确写法是先 `ms = dict(session.mission_state)` 再改、再赋值。
- 期限 12 回合比较合适（3 阶段）；设 3-6 回合会因为每回合消耗 + 恶化惩罚，在第二三回合就失败。
- 回溯（rewind）会按保留回合数重算 `days_left`，但已走过的阶段不回退。

## 14. 前端交互约定（改之前先看这几条）

- **对局 URL 必须带会话 id**：`/game/<id>`。之前创建后跳 `/game`，刷新会被 `requiresGame` 守卫打回主界面，登录回跳也会丢局。`GameView` 挂载时若发现无 id 但有会话，会 `router.replace` 补齐。
- **响应体只能读一次**：`response.json()` 之后再 `response.text()` 会抛 `body stream already read`。统一先 `text()` 再 `JSON.parse`（见 `stores/game.js`）。
- **流式生成时不要预先清空剧情**：`performAction` 里保留上一段，等第一个 `story_chunk` 到达再替换；否则中途失败会留下空白页。
- **布局三条不许重叠**：顶部栏 < 使命条 < 剧情面板 < 底部行动栏。手机端剧情面板用 `bottom: calc(var(--bottom-bar-h) + 8px)` 定位，**不要给它设 `top`**，否则会压住行动选项。使命条的下移规则只在 `min-width: 601px` 生效。
- **离开对局不需要确认**：进度实时入库，侧栏用「← 回到主界面」，不弹 `confirm`、不清空会话。
- 登录：`/login?redirect=<当前页>`，`api` 拦截器 401 时会带上当前地址；没有回跳参数时，若内存里还有对局，直接接着玩。

## 15. LLM 链路与故障转移

主链路：DeepSeek 直连（`DEEPSEEK_BASE_URL`）。备用：阿里云百炼兼容端点
（`LLM_FALLBACK_BASE_URL`）+ 同名模型 `deepseek-v4.1-flash`，选项生成用 `qwen-plus`。

三层保护，对应三种真实故障：

| 故障表现 | 机制 | 配置 |
|---|---|---|
| 上游 503 / 连接失败 / 限流 | 主链路异常立刻切备用（同步、异步、流式三条路径都已包） | `LLM_FAILOVER_ENABLED`、`LLM_PRIMARY_MAX_RETRIES=1` |
| 上游排队，几十秒不吐第一个字 | **首字看门狗**：8s 没首字就关掉主链路、用备用重开一路流 | `LLM_FIRST_TOKEN_TIMEOUT` |
| 选项生成慢/卡住 | 元数据单独超时 25s，超时先给默认选项；主 → qwen-plus | `LLM_METADATA_TIMEOUT`、`LLM_FALLBACK_METADATA_MODEL` |

上下文压缩（`context_compressor.py`）也走同样的备用逻辑，避免上游繁忙时压缩连续失败、历史越滚越长。

调参建议：主链路超时不要超过 45s，重试不要超过 1 次——重试越多，用户等得越久，而 503 通常重试也不会好。

## 16. 使命失败、第二幕与终局

- **失败**：`mission_state.status = "failed"`，成就记「使命未竟」。故事不结束。
- **下一幕**：失败后的下一个回合，`GameService.enter_next_act()` 取最近 3 段剧情 + 失败使命的标题/目标/赌注/阶段/最后判定，调 `provider.generate_next_act()` 生成这一幕专属的新使命（接着失败的具体后果写，不重复上一幕目标）；LLM 失败才退回通用模板。`act` 每次 +1（第二/第三幕……），每幕 10 回合。前端使命条按 `act` 显示「第 X 幕」。
- **死亡终局**：裁判 `judge_mission()` 额外返回 `character_dead`（只有明确断气才算，受伤/被抓/濒死都不算）。为 true 时 `status="dead"`，之后所有行动接口返回 **409 + `detail.ended=true`**。
- 前端 `mission.status === 'dead'` 时显示终局面板（结局文案、积分、成就、用同一角色重开），并隐藏行动栏。`mission` 计算属性以会话状态优先，避免被上一回合的 scene 快照盖回去。

## 17. 自定义角色（私有存档）

表 `custom_characters`：`user_id` + `novel` + 姓名/性别/年龄/身份/背景。接口 `/api/custom-characters`（增删改查都按 `user_id` 过滤，别人的角色一律当 404）。

- 未登录调用创建接口 → 401；游客仍可开局，只是不保存。
- 前端在角色页顶部列出「我的角色 · 只有你能看见」，点卡片直接进入时间选择；✎ 修改、✕ 删除。
- 开始游戏时如果是自定义角色且已登录：有 `editingCustomId` 就 PUT，否则 POST。保存失败只 `console.warn`，不挡开局。
- 自定义角色的使命由 `provider.generate_mission()` 按背景现拟。

## 18. 批量生成使命（其余 12 个世界）

`scripts/gen_missions.py`：一个角色一次调用，产出它所有时间节点的使命；已有 mission 的节点跳过（断点续跑）。

```bash
cd backend && /opt/venv/bin/python ../scripts/gen_missions.py --concurrency 5 --skip 废土末世
```

- **必须从 `backend/` 目录运行**：`Settings` 读的是当前目录的 `.env`，否则报 `SECRET_KEY Field required`。
- 世界包字段是 `novel` 不是 `name`，脚本取 `world.get('novel')`。
- 生成的使命统一 `deadline_turns=12`。
- 生成后要跑 `import_content.py import` 才会进库。
- 给自定义角色现拟使命时模型会返回空 content（思考被打开），必须显式关思考 + 空响应重试。
