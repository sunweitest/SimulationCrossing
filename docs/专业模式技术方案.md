# 专业模式技术方案（草稿 v0.1）

> 目标读者：项目所有者。这份文档只讲「怎么实现、要花多少、有什么风险」，看完再决定做不做、做哪一档。
> 娱乐模式 = 现在线上跑的这套，不改、不迁移。

---

## 1. 为什么要分模式

现在的链路是**一次调用出全部**：拼提示词 → 一次流式生成剧情 → 并行生成 3 个选项 → 再判使命。优点快（P50 6–9 秒）、便宜、稳定；缺点也很明确：

| 现在的限制 | 玩家能感知到的表现 |
|---|---|
| 只有一条叙事线，所有 NPC 由同一个模型在同一段文字里"顺带"演 | 多人同场时，配角只会说一句功能性的台词，没有自己的目的 |
| 没有"谁知道什么"的概念 | NPC 会用上帝视角说话：没在场的人知道刚发生的事；刚认识的人知道你的秘密 |
| 状态存在 `characters_state` 的 JSON 里，靠每回合重新提取 | 长局之后人物前后不一致（性格、称呼、立场漂移） |
| 回溯 = 删掉历史行回退积分 | 只能回到"之前某一回合"，回到中间状态（某个 NPC 已倒戈但剧情没写）做不到 |
| 一次生成失败只能整回合重来 | 玩家等了 20 秒，重试又是 20 秒 |

**专业模式解决的就是这四件事**，代价是每回合更慢、更贵。所以它不能是默认模式。

### 两种模式的边界（产品口径）

| | 娱乐模式（默认） | 专业模式 |
|---|---|---|
| 一句话 | 一个人的故事，写得快、写得爽 | 一群人的局，谁都知道什么、谁都在算自己的账 |
| 单回合延迟 | P50 6–9s | 目标 P50 12–16s，P95 ≤ 22s |
| 单回合成本 | 1× | 约 3–4.5×（按 token 计） |
| 适合的世界 | 全部 16 个 | 多角色世界优先：红楼梦、金瓶梅、都市霸总、深宫（待做） |
| 回退能力 | 回到某一回合（删行） | 回到任意 checkpoint（含"这次 NPC 行动没提交"的中间态） |
| 玩家可感知的差异 | 快、直接、每回合都有 3 个选项 | 先看到"谁在做什么"，再看到叙事；NPC 会主动出手；同一件事被不同人转述会走样 |

**不做成"更贵的同款"**：如果专业模式只是把一次调用拆成三次，玩家只会觉得变慢了。它必须有娱乐模式给不了的东西——下面第 3 节的"知识可见性"就是那个东西。

---

## 2. 目标与非目标

**目标（v1，可上线的最小专业模式）**

1. 进入穿越前可选模式；模式写进会话，存档列表能看到徽标。
2. 一回合 = 一次 graph 运行：导演 → 多个 NPC 并行行动 → 叙事合成 → 裁判 → 提交。
3. 每个 NPC 只拿到**自己知道的事实**，不得使用全局视野。
4. 每回合结束落 checkpoint；进程被杀、模型超时，能从中断处 resume 到同一回合。
5. 任一步失败可降级：直接用现有娱乐模式链路出文，保证玩家不会卡死。
6. 娱乐模式行为零变化（QA 52/52 必须保持）。

**非目标（明确不做）**

- 不做多人实时对局；不做语音；不做玩家自定义 NPC 脚本。
- v1 不做"NPC 之间自由对话 N 轮"，只做一次并行表态（成本会失控）。
- v1 不做向量 RAG（见 §9，pgvector 当前未装，先做结构化事实 + 关键词召回）。
- 不追求专业模式也能 5 秒出结果——它的卖点是质量，不是速度。

## 3. 核心设计

### 3.1 一回合的 graph

```
                       ┌──────────────────────────────┐
   玩家行动 ─────────▶ │ intake      读会话/状态/模式   │
                       └──────────────┬───────────────┘
                                      ▼
                       ┌──────────────────────────────┐
                       │ cast        选本回合在场的人   │  ← 关系预取（已上线）
                       │             + 场景涉及的地点   │
                       └──────────────┬───────────────┘
                                      ▼
                       ┌──────────────────────────────┐
                       │ recall      每人取"他知道的事" │  ← facts 过滤（核心）
                       └──────────────┬───────────────┘
                                      ▼
                       ┌──────────────────────────────┐
                       │ director    定本回合冲突/节拍  │  ← 强模型，全知视角
                       └──────────────┬───────────────┘
                          ┌───────────┴───────────┐
                          ▼           ▼           ▼
                    ┌─────────┐ ┌─────────┐ ┌─────────┐
                    │ npc_a   │ │ npc_b   │ │ npc_c   │  ← 并行，各自只见局部
                    └────┬────┘ └────┬────┘ └────┬────┘
                          └───────────┼───────────┘
                                      ▼
                       ┌──────────────────────────────┐
                       │ narrator    合成叙事（流式）   │
                       └──────────────┬───────────────┘
                             ┌────────┴────────┐
                             ▼                 ▼
                       ┌──────────┐      ┌──────────┐
                       │ judge    │      │ options  │      ← 并行
                       │积分/使命  │      │ 3 个选项  │
                       └────┬─────┘      └────┬─────┘
                            └────────┬────────┘
                                     ▼
                       ┌──────────────────────────────┐
                       │ commit      写库 + facts 增量  │
                       └──────────────┬───────────────┘
                                      ▼
                                 checkpoint
```

节点数 7，串行深度 4（intake/cast/recall 可合并成一次准备），最关键的是 **director 之后的并行扇出**：3 个 NPC 同时跑，把"多步"带来的延迟压回可接受范围。

### 3.2 状态（StateGraph 的 State）

用 Pydantic 模型，字段和现库结构对齐，避免两套概念：

```python
class ProState(BaseModel):
    # 会话
    session_id: int
    turn: int
    mode: Literal["fun", "pro"] = "pro"
    novel: str
    timeline: str

    # 玩家
    player: PlayerState          # name/identity/age/gender/status/attrs

    # 本回合
    action: str
    cast: list[CastMember]       # name/identity/在不在场/关系/好感/他已知的 facts id
    director_brief: DirectorBrief  # 冲突、节拍、允许谁知道什么、预期后果
    npc_actions: list[NpcAction]   # 每人一句"我这一回合做什么"，含动机
    narration: str
    choices: list[Choice]

    # 世界事实
    facts: list[Fact]            # id / text / turn / audience(list[str]|["*"]) / source
    relations: dict[str, Relation]

    # 判定
    mission: MissionState
    points_delta: int
    achievements: list[str]
    character_dead: bool

    # 运行
    phase: str                   # 供 SSE 推送
    cost: CostLedger             # tokens / ms / model
    fallback_used: bool
```

### 3.3 知识可见性（专业模式的价值所在）

这是整个方案里唯一"非它不可"的部分，也是最容易被做错的部分。

**事实表（facts）**：每条事实带 `audience`——谁知道它。

```json
{"id": "f_0012", "turn": 7, "text": "王熙凤私下把账房的银子挪去放贷", "audience": ["王熙凤", "平儿"], "source": "player_action"}
{"id": "f_0013", "turn": 9, "text": "宝玉夜里去过梨香院", "audience": ["*"], "source": "narration"}
```

规则：

- `audience: ["*"]` = 公开事实（在场所有人、后续可被街谈巷议得知）。
- NPC agent 的提示词只拼 `audience` 含自己名字、或 `*` 的事实；**绝不拼全量**。
- 玩家知道的事实由玩家自己的行动与在场记录产生。玩家不在场时发生的事，玩家也看不到（narrator 只能写"你听说"）。
- 新增事实只能由 judge 在 commit 阶段写入，且必须给出 audience；给不出就按 `*` 处理（保守公开，避免 NPC 出现"神秘全知"）。

**为什么这比"多调几次"值钱**：玩家第一次体验到"我骗了他，而另一个知道他底细的人在场"，是现在的单线叙事写不出来的。这也是宫斗/乙女这类题材真正需要的东西。

### 3.4 checkpoint 与回溯

- `thread_id = f"session:{session_id}"`，`checkpoint_ns = mode`。
- 存储：LangGraph 的 `AsyncPostgresSaver`，建在同一个库（三张表：`checkpoints` / `checkpoint_blobs` / `checkpoint_writes`），不引入新中间件。
- 每回合 commit 后写一次 checkpoint；`interrupt_before=["narrator"]` 可选（调试用）。
- **回溯**：现有回溯是"删掉 turn > N 的行 + 回退积分"。专业模式改为"读 turn N 的 checkpoint 恢复 state，再截断 facts/relations 到该回合"，不删剧情行（保留审计），前端只展示到 N。这样玩家能回到"某个 NPC 已经动摇、但还没表态"的中间态。
- **故障恢复**：进程重启后 `graph.ainvoke(None, config)` 从最后 checkpoint 继续；如果是 narrator 流式中途断开，重跑 narrator 节点即可（NPC 行动结果已在 checkpoint 里，不会重复计费）。

### 3.5 模型分层与预算

| 节点 | 模型 | 理由 | 预算 |
|---|---|---|---|
| cast / recall | 无 LLM（规则 + 预取） | 零成本 | ~0ms |
| director | 主模型（DeepSeek） | 需要全局视野与判断 | ≤ 3s，800 tokens |
| npc_a/b/c | 备用模型 `qwen-plus` 或 `deepseek-v4.1-flash` | 短输出（≤200 tokens）、并行、便宜 | ≤ 4s，每个 300 tokens |
| narrator | 主模型，流式 | 文笔决定体验，不能降级 | 首字 ≤ 8s（沿用看门狗） |
| judge | 主模型（可与 options 并行） | 判使命要准 | ≤ 3s |
| options | 备用模型 | 短输出 | 25s 超时兜底（沿用） |

预计：输入 tokens ≈ 现在的 2.2×，输出 ≈ 3.5×，**成本约 3–4.5×**。按当前日活与免费额度（5/8 次）看，专业模式应当**默认关闭、且不计入免费额度**（或者单独给 1 次/天试用），否则成本不可控——这一点需要你拍板（见 §11）。

### 3.6 失败与降级

| 失败点 | 处理 |
|---|---|
| director 失败/超时 | 直接降级到娱乐模式链路出文，标记 `fallback_used=true`，前端不报错 |
| 某个 NPC agent 失败 | 该 NPC 本回合不行动（不阻塞其他人），继续 narrator |
| narrator 首字 8s 无输出 | 切备用模型重开（沿用现有看门狗） |
| judge 失败 | 使命保持 active、积分给 0，回合照常提交（宁可少判，不可卡局） |
| commit 失败 | 整回合回滚到上一个 checkpoint，返回 500 + 可重试提示（玩家不扣次数） |

## 4. 数据模型变更

```sql
-- 1) 会话加模式
ALTER TABLE game_sessions ADD COLUMN mode varchar(8) NOT NULL DEFAULT 'fun';
CREATE INDEX ix_game_sessions_mode ON game_sessions (mode);

-- 2) 事实库（专业模式专用；娱乐模式不写）
CREATE TABLE session_facts (
  id            bigserial PRIMARY KEY,
  session_id    integer NOT NULL REFERENCES game_sessions(id) ON DELETE CASCADE,
  turn          integer NOT NULL,
  text          text NOT NULL,
  audience      jsonb NOT NULL DEFAULT '["*"]'::jsonb,   -- 角色名数组，或 ["*"]
  source        varchar(24) NOT NULL,                    -- player_action / narration / npc / judge
  created_at    timestamp without time zone NOT NULL DEFAULT (now() AT TIME ZONE 'Asia/Shanghai')
);
CREATE INDEX ix_session_facts_session_turn ON session_facts (session_id, turn);

-- 3) 回合审计（两种模式都写，便于比较成本与延迟）
CREATE TABLE agent_runs (
  id            bigserial PRIMARY KEY,
  session_id    integer NOT NULL,
  turn          integer NOT NULL,
  mode          varchar(8) NOT NULL,
  node          varchar(24) NOT NULL,
  model         varchar(48),
  prompt_tokens integer DEFAULT 0,
  output_tokens integer DEFAULT 0,
  latency_ms    integer DEFAULT 0,
  ok            boolean DEFAULT true,
  error         text,
  created_at    timestamp without time zone NOT NULL DEFAULT now()
);

-- 4) LangGraph checkpoint（由 AsyncPostgresSaver.setup() 建，不手写迁移）
```

迁移文件：`e5f6a7b8c9d0_pro_mode.py`，`down_revision="d4e5f6a7b8c9"`。三张新表 + 一列，娱乐模式不受影响（`mode` 默认 `fun`）。

## 5. 后端实现

### 5.1 依赖

```text
langgraph>=0.2
langgraph-checkpoint-postgres>=2.0
psycopg[binary,pool]>=3.2      # AsyncPostgresSaver 用 psycopg3，不是 asyncpg
```

**注意**：现有项目用 asyncpg（SQLAlchemy async），LangGraph 的 PG saver 用 psycopg3。两者可以共存，但要单独配一个 `psycopg_pool.AsyncConnectionPool`，连接串用 `postgresql://` 而非 `postgresql+asyncpg://`。这是引入 LangGraph 最容易被忽略的一处。

### 5.2 代码落点

```
backend/app/agents/
  state.py          # ProState / Fact / NpcAction（Pydantic）
  graph.py          # build_graph(): StateGraph 装配
  nodes/
    prepare.py      # intake + cast + recall
    director.py
    npc.py          # 单 NPC 行动（并行扇出）
    narrator.py     # 流式合成
    judge.py        # 积分/使命/死亡/新事实
    commit.py
  checkpoint.py     # AsyncPostgresSaver 单例 + setup()
  fallback.py       # 降级到 game_service.call_llm_api
```

与现有代码的边界：

- **复用**：`get_provider()`、`_PROMPTS` 世界 prompt、`_inject_character_context`（变成 cast 节点的输入）、`quota`、`rate_limit`、`mission` 判定函数、`scene_image_matcher`。
- **不碰**：`game_service.stream_story_text`（娱乐模式继续用）、现有 API 路由（专业模式新增 `POST /api/game/action/pro/stream`，不动旧端点）。

### 5.3 接口

```
POST /api/game/session                { ..., "mode": "fun" | "pro" }   # 新增可选字段
POST /api/game/action/pro/stream      { game_session_id, action }      # 新增，SSE
GET  /api/game/session/{id}/timeline  # 返回 turn 列表 + 每回合是否有 checkpoint
POST /api/game/session/{id}/revert    { turn }                          # 专业模式回溯（保留剧情行）
GET  /api/game/session/{id}/facts     { turn? }                         # 调试/展示"谁知道什么"
```

SSE 事件（在现有 `chunk` / `scene` 之外新增）：

```
event: phase   data: {"phase":"cast","names":["王熙凤","平儿"]}
event: phase   data: {"phase":"director","beat":"她要试你"}
event: npc     data: {"name":"王熙凤","intent":"把话挑明，看你怎么接"}
event: chunk   data: {"text":"…"}          # narrator 流式，沿用现有格式
event: scene   data: {…}                   # 沿用现有格式，前端零改动可跑
```

关键：**专业模式最后仍然发一个 `scene` 事件**，格式和娱乐模式一致，所以前端可以先只加"阶段进度条"，其余不动。

## 6. 前端改动

1. **模式选择**：`CharacterCreateView` 的「开始穿越」上方加一个二选一（娱乐/专业），专业模式默认灰一点、写清代价：
   > 专业模式：每回合更慢（10–20 秒），但每个角色有自己的目的，谁不知道什么会真的影响剧情。每天 1 次体验额度。
2. **进度条**：专业模式流式前显示 `选角 → 定调 → 角色行动 → 落笔`，用 `phase` 事件驱动。这一步很关键——12 秒没有反馈会被当成卡死。
3. **NPC 行动卡**：`npc` 事件渲染成叙事上方的折叠条（"王熙凤：把话挑明，看你怎么接"），可关。
4. **存档徽标**：`MyGamesView` / `LadderView` 显示 `专业` 角标。
5. **回溯选择器**：专业模式展示 turn 列表并调用 `/revert`。

## 7. 验收标准

| 项 | 口径 | 门槛 |
|---|---|---|
| 一致性 | 30 条"谁知道什么"测试：给 NPC 一个只有别人知道的事实，问他是否知情 | 正确率 ≥ 90% |
| 角色主动性 | 10 局人工评：NPC 是否做过"没有被玩家要求"的行动 | ≥ 7 局有 |
| 延迟 | 真实对局 50 回合，P50 / P95 | ≤ 16s / ≤ 22s |
| 成本 | 单回合 tokens 与费用（对比娱乐模式） | 报告数字，不设硬门槛 |
| 恢复 | 回合中途 `kill -9` uvicorn，重启后 resume | 同一回合续上，不重复扣次数 |
| 降级 | 把 director 模型名改错，跑一回合 | 仍能出文，`fallback_used=true` |
| 回归 | 娱乐模式 QA 套件 | 52/52 不变 |

## 8. 分期与工作量

| 阶段 | 内容 | 我这边估时 | 你可感知的产出 |
|---|---|---|---|
| P0 | `mode` 字段 + 迁移 + 创建页开关 + graph 骨架（director→narrator→judge，单 NPC）+ 降级 | 2–3 天 | 能选专业模式，能跑完一局，但"多人同场"还没体现 |
| P1 | 多 NPC 并行 + facts/audience + commit 写事实 + checkpoint + resume | 3–4 天 | 真正的"谁不知道什么"；重启不丢进度 |
| P2 | 回溯接 checkpoint + 审计面板（每回合各节点耗时/tokens）+ 限流与配额 | 2–3 天 | 可运营：能看到成本，能控制谁用 |
| P3（可选） | 事实 RAG（pgvector 或 pg_trgm + 现有 embedding）+ NPC 长期记忆摘要 | 3–5 天 | 长局一致性明显提升 |

**P0+P1 是一组**（约 5–7 天），单独做 P0 玩家感知不到价值，不建议只做 P0。

## 9. 关于 RAG 的说明

- 当前库只有 `pg_trgm`，**没有 pgvector**。要装：`apt install postgresql-16-pgvector`，或者用 `pg_trgm` 做关键词召回（够用，成本低）。
- 专业模式 v1 的事实召回不靠向量：直接把"本回合在场的每个 NPC 的 audience 过滤后的 facts"拼进 prompt，条数天然可控（一局 30 回合通常 < 80 条）。
- 真正需要向量的是**跨局的世界知识**（原著设定、几万字的世界观），那是 P3，且可以先用现有的百炼 embedding + 一个 JSON 缓存文件顶一阵。

## 10. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 延迟翻倍，玩家在 12 秒里流失 | 留存 | 阶段进度条 + 首回合用娱乐模式预热；P95 超 22s 自动降级 |
| 成本 3–4.5×，免费额度被薅 | 钱 | 专业模式单独配额（1 次/天，登录用户），或只给付费/包月用户 |
| 「谁不知道什么」写错 → NPC 变全知 | 体验崩 | facts 必须由 judge 产出、代码侧强制过滤，不靠 prompt 自觉 |
| LangGraph 版本破坏性变更 | 维护 | 锁版本；graph 只依赖 StateGraph/checkpoint 两个稳定 API；provider 层自研不变 |
| psycopg3 与 asyncpg 混用出错 | 启动失败 | 独立连接池，只给 saver 用；`setup()` 只在启动时跑一次 |
| 两套链路并存，功能漂移 | 维护 | 娱乐模式代码冻结；专业模式只新增文件，不改旧路由 |
| 回溯语义变复杂（删行 vs 截断） | 数据错乱 | 专业模式走 `/revert`，娱乐模式保持删行；两个入口互斥 |

## 11. 需要你拍板的四件事

1. **专业模式给谁用**：① 所有登录用户 1 次/天试用；② 只给包月/付费用户；③ 先只给你自己的账号（灰度）。
2. **默认模式**：新用户默认娱乐（推荐），还是按世界推荐（多角色世界弹一次"要不要试专业模式"）。
3. **做哪一档**：只做 P0+P1（≈5–7 天，能演示"谁不知道什么"），还是一次做到 P2（≈8–10 天，可运营）。
4. **世界范围**：v1 只做红楼梦 / 金瓶梅 / 都市霸总三个世界的专业 prompt 资产，还是一次全铺（16 个世界，内容工作量翻倍）。
